# 裁决记录

## 提案文档 untracked 未提交 — 偏离（需求来源带入）

1. **问题证据**：`git status` 显示主工作区 `docs/planning/提案-改名portunnel与数据迁移.md` 为未跟踪文件。Worktree 隔离规则要求「主工作区中未提交的改动与未跟踪文件一律不带入、不参考」；但该文件是本需求的需求来源（讨论轮用户逐项拍板、status: accepted），阶段 0 规定需求基线落盘自需求文档。两条规则字面冲突。
2. **备选方案**：a) 先在主工作区提交提案文档再建基线——会在开发分支产生用户未要求的提交，用户指令仅为「落盘前切到 V2.0 分支」，且该分支工作区尚有其他 untracked 提案，提交范围难以干净切分；b) 将提案内容完整并入 worktree 内 `需求基线.md`，原提案保持 untracked——代码基线纯净性不受影响（该文件非代码）。
3. **裁决**：选 b。基线内容以并入后的 `需求基线.md` 为准。
4. **理由**：worktree 隔离的目的是保证实现现场干净（防未提交代码改动混入 commit）；提案是需求文档而非实现产物，主控编辑基线文件属于阶段 0 职责。基线.md 成为唯一需求权威来源，后续 subagent 不依赖主工作区文件。依据「用户拍板内容即完整需求」假设推进；若被推翻（用户补充新需求），波及范围是基线更新与已派发工作的返工。
5. **影响**：需求对照入口从原提案转移至 `需求基线.md`；范围、验收标准（B1–B7）、约束（C1–C8）不变。另记：`.gitignore` 缺 `.worktrees` 条目属流程明文规定行为（不混入 commit、提示用户处理），不构成裁决，仅记入执行台账环境记录。

## TunnelEditor localStorage key「sshmgmt.editor.tab」— 放弃（不改）

1. **问题证据**：方案 §9 待裁决项与 §7 明确不改清单指出 `src/components/TunnelEditor.tsx:24` 的 `TAB_STORAGE_KEY = "sshmgmt.editor.tab"` 不在基线 G1「repo/安装包/应用名/crate/npm 包名/文档/CI 文案」与 D 清单任何一类内；我已复核该行确实存在（`TunnelEditor.tsx:24,30,42`）。
2. **备选方案**：a) 改新 key `portunnel.editor.tab`——收益仅消除一处代码内旧名，代价是所有用户已保存的表单 Tab 偏好丢失（key 变即读不到旧值）；b) 不改——零收益损失、零风险；c) 新 key + 读旧 key fallback——兼顾但引入冗余双 key 逻辑，超出本需求范围。
3. **裁决**：选 b（不改）。
4. **理由**：基线 G1 名称类别的划分依据是「用户可见的品牌暴露或对外标识」；localStorage key 既不可见也无对外语义，且改名直接损伤一项用户偏好数据——与「平稳过渡」目标相悖。基线未要求，范围外改动不予引入。
5. **影响**：无代码改动；该 key 永久保留 `sshmgmt` 前缀，属有意为之的底层兼容残留，记录在案供后续对照。

## C6「数据各自独立会分叉」— 改写（措辞修正为「配置独立、钥匙串共享」）

1. **问题证据**：基线 C6 原文「新旧并存期间数据各自独立会分叉会分叉」；方案 D7 指出事实是配置目录独立（`portunnel/` vs `sshmgmt/`）而钥匙串 service 名不变（C2）故密码实际互通。我已核实 `store.rs` 的 `KEYRING_SERVICE` 与目录派生是两个独立常量，该事实成立。
2. **备选方案**：a) 沿用 C6 原文「数据各自独立」——表述不准确（密码互通），会误导用户以为密码也分叉；b) 改为「配置各自独立、会各自分叉（钥匙串密码为二者共用）」——精确且不改变 C6 意图（提醒卸载旧版）。
3. **裁决**：选 b。
4. **理由**：C6 的目标是防止新旧并存造成配置混乱，精确表述更能达成该目标；属措辞细化，不改变验收标准 B1–B7 与任何约束。
5. **影响**：README 新增段落与 releaseBody 文案按此措辞落地（方案 S12/S14）；无验收标准变化。

1. **问题证据**：评审报告 §1.2 P1 指出 `.github/workflows/release.yml:68` 的 releaseBody 为「新旧并存配置各自独立、会各自分叉」，缺「（钥匙串密码为二者共用）」；我已核对 README.md:49 有该括注、release.yml 没有。本记录第 3 条裁决原文：「README 新增段落与 releaseBody 文案按此措辞落地（方案 S12/S14）」——基线 C6 的发布文案要求覆盖 releaseBody，属承诺未完整落地。
2. **备选方案**：a) 接受现状（README 已写全）——但裁决第 3 条明确点了 releaseBody，接受即等于默许裁决未执行；b) 打回原实现者补齐括注——一行文案改动，无代码风险；c) 把「releaseBody 不含括注」升级为新裁决——实为放弃原裁决，无事实依据。
3. **裁决**：选 b，打回 impl-portunnel 修正。
4. **理由**：裁决第 3 条是已确认结论，评审发现落地不完整属实现缺陷而非需求变更；修正成本为一行文案，风险极低。依据「README 与 releaseBody 需同口径」的事实推进。
5. **影响**：release.yml 一行改动；需复跑 YAML 解析；不影响验收标准与代码。

## 评审 P2：StrictMode 开发态重复弹警告 — 放弃（降级为已知遗留风险）

1. **问题证据**：评审报告 §1.3 P2；我已核实 `src/main.tsx:6` 启用了 `React.StrictMode`，开发态 effect 双跑会让启动警告 banner 出现两条。生产构建（`vite build`）不启用 StrictMode 双跑，且该警告为一次性迁移失败提示，无数据副作用。
2. **备选方案**：a) 用 `useRef` 守卫只弹一次——增加 3 行状态代码，违背方案「不新增状态」的简洁性；b) 降级为已知遗留风险并记录——开发态视觉重复，生产无影响；c) 关闭 StrictMode——会削弱整个项目的开发期双跑检查，代价远大于收益。
3. **裁决**：选 b，降级为遗留风险。
4. **理由**：影响面仅限开发者本地开发态、仅视觉重复、无数据或功能后果；为一行警告引入守卫状态不值得。依据「生产构建不受影响」的已核实事实推进。
5. **影响**：无代码改动；写入终态汇报的遗留风险清单与变更摘要（由主控在终态说明，不要求代码注释）。

## 评审 P3：迁移失败文案缺旧目录路径 — 改写（打回修正）

1. **问题证据**：评审报告 §1.3 P3 指出 `store.rs` 迁移失败文案只给新目录（`new_dir.display()`）或完全不给路径，未给旧目录绝对路径；实施计划 §5 风险表原文承诺「警告文案给出旧目录位置与手动复制路径」——承诺未落地。
2. **备选方案**：a) 接受现状——文案虽有「旧数据仍保留」，但用户无法定位旧目录（尤其 macOS 路径较深），与承诺不符；b) 打回实现者在两条失败文案中补上旧目录绝对路径——与 P1 同批修正，无额外风险；c) 改写实施计划承诺——削弱用户在迁移失败时的自救能力，与 B6「用户可感知」目标相悖。
3. **裁决**：选 b。
4. **理由**：这是实施计划自身承诺的落地缺口，修正仅改两处 `format!` 文案；单测 `partial_failure_warns` 断言「消息含 tunnels.json」仍成立，但需同步确认文案变更后测试仍通过。依据「文案改动不影响迁移逻辑」推进。
5. **影响**：store.rs 两处文案；单测需复跑；B6 沙箱日志内容随之变化（断言逻辑不变）。
