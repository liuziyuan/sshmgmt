# 裁决记录：多语言（i18n）

## A5 parser 单测数量 — 偏离

1. **问题证据**：设计文档 §4-D 组末尾写「既有 33 个单测」（L474），同文档 S5 完成判定写「parser 既有 25 个解析单测全绿」（L529），自相矛盾；设计 agent 回报自检声称已修正为 25 但 L474 漏改。触及需求 A5「`cargo test` 通过」的作证口径。主控实测 `grep -c '#\[test\]' src-tauri/src/parser.rs` = **25**。
2. **备选方案**：(a) 续跑原 design agent 修正该一处数字——保留其上下文，改动面最小；(b) 主控亲自改设计文档——违反「主控不亲自写设计」角色边界；(c) 不修正，口头告知实现者以 25 为准——文档是实现的唯一权威输入，留矛盾会让实现者误判测试缺失。
3. **裁决**：选 (a)，续跑 design-i18n 修正一处数字。
4. **理由**：主控已实测正确值，修正指令明确、验证方式（grep 自检）写死，一轮可收口；(b)(c) 各有角色边界或权威性缺陷。
5. **影响**：不改变设计主体与任何需求条款；实现阶段 S5 的测试数量判定以 25 为准。属「缺口即续跑」的轻量修正，不计入设计质量修正轮次（idle 修正性质）。

## A2/G4 托盘启动兜底语言 — 新增

1. **问题证据**：设计文档 §9-J1 与风险 R4：托盘菜单初始文案由 Rust 硬编码构建，前端接管前英文用户会短暂看到中文托盘（约 1-2 秒）。触及 A2「托盘菜单随语言重建」的实现时序，需求基线未规定启动瞬间的兜底语言。
2. **备选方案**：(a) zh 硬编码兜底 + 前端 mount 即重建（设计推荐）；(b) 后端引入 sys-locale 预检测系统语言构建初始托盘——消除闪变，但新增依赖、且「语言真相」分裂为后端检测 + 前端选择双源，违背 C6（后端不感知语言）与 D3 精神。
3. **裁决**：采纳 (a)。
4. **理由**：与 fallbackLng（zh）一致；零新依赖；单源真相保持「文案由前端传入」；1-2 秒托盘闪变对工具型应用影响极小且仅在英文用户首次启动出现。依据充分。
5. **影响**：英文用户启动瞬间托盘短暂中文列为终态汇报的已知现象（遗留说明项，非缺陷）；不新增任何需求条款之外的验证。

## A5 Msg 变体粒度 — 新增

1. **问题证据**：设计文档 §9-J2：`Msg` 枚举按 65 个独立变体设计，备选为参数化归并到约 30 个（如 connectStepFailed{layer,stage}）。触及 A5「消息码枚举双侧一致且全有文案」的落点规模。
2. **备选方案**：(a) 65 独立变体（设计推荐）；(b) 参数化归并 ~30 个——枚举体积减半，但 locales 需大量条件模板/嵌套 key，插值缺失时句子破相，多跳措辞与排障信息（「通过上一跳」）丢失精度。
3. **裁决**：采纳 (a)。
4. **理由**：文案精度零损失、locales 模板无条件分支、check-msg-codes 一一对应更简单；枚举体量大是实现阶段的机械化成本，不构成设计风险。依据：设计 §2.1 已给出全量变体与逐处映射，粒度成本可见可控。
5. **影响**：model.rs / types.ts / locales 三处各 65 条同步义务（三层防护已覆盖）；无需求条款变化。

## A4 静态 UI key 校验范围 — 新增

1. **问题证据**：设计文档 §9-J3：`check:i18n` 脚本校验 zh/en key 集合相等与 `msg.*` ↔ Msg 变体相等，但「代码引用的静态 key 是否存在」未校验。触及 A4「key 缺失回退 zh、一致性校验存在且通过」的覆盖范围界定。
2. **备选方案**：(a) 不校验静态 key，fallback zh + S10 残留 grep 兜底（设计推荐）；(b) 引入 i18next 类型生成器或 AST 扫描——编译期/仓库期拦截所有 key 拼写错误，但新增工具链依赖与生成步骤（设计 §7-X5 已论证否决类型生成器）。
3. **裁决**：采纳 (a)。
4. **理由**：本项目 key 规模约 200，静态 key 拼写错误的实际暴露面是「个别界面显示 code/中文兜底」，走查即见、修复成本一行；为此前置 AST/类型生成工具链，收益不抵成本。msg.*（后端消息）已由脚本严格校验，那是无法走查全覆盖的部分，校验优先级正确。
5. **影响**：A4 验收口径维持「`npm run check:i18n` 真实跑通」（zh/en 相等 + msg 变体相等）；静态 key 的拼写错误风险列为可接受的低风险（评审阶段如发现具体漏网 key，按缺陷处理而非范围问题）。
