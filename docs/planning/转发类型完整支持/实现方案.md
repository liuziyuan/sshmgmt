# 实现方案：转发类型完整支持（-D / -R / -J）

> 基线：《需求基线-转发类型完整支持》（frozen，commit 43ed390）；架构决策①~⑦见《提案-转发类型完整支持》§5，本方案不推翻。
> 事实基础：russh 0.44.1 / russh-keys 0.44.0（Cargo.lock 实锁版本）API 已逐条查证，见 §9 附录。本机无 cargo 环境、`~/.cargo/registry` 不存在，查证按基线 §5 允许的降级途径走 docs.rs + GitHub v0.44.1 tag 源码。

## 1. 总览

三期各自独立升版、独立验证，代码落点高度共享一套骨架：

| 期 | 版本 | 核心增量 | 新文件 | 主要落点 |
|---|---|---|---|---|
| 一 | v1.3.0 | `-D` SOCKS5 动态转发 | `src-tauri/src/socks.rs` | model / parser / tunnel / 前端渲染 |
| 二 | v1.4.0 | `-R` 远端转发（回调架构） | 无 | tunnel（SshClientHandler 扩展）/ parser / probe |
| 三 | v1.5.0 | `-J` 多跳（链式模型重构） | 无 | model（hops+迁移）/ tunnel（逐跳链）/ parser / store |

与 `tunnel.rs` 状态机的接入点（三期共同骨架，均不改 `run_tunnel` 外层循环）：

```
run_tunnel（外层 Connecting→Connected/Failed/Reconnecting 循环，三期不动）
 └─ connect_and_forward
     ├─ select! 竞速区间（不变式 1：三期新增任务一律不进此区间）
     │   └─ establish_session ── v1.3: :22 预检按 kind 跳过 Dynamic
     │                        ── v1.4: 返回值扩展 forward_rx（-R 推送通道）
     │                        ── v1.5: 重构为逐跳链 hops[0..n]，每跳两阶段认证
     ├─ 【v1.4 新增，绿灯前置】逐条 Remote 规则 session.tcpip_forward()，
     │   失败按 §4.5 分类：RequestDenied→Fatal，其余→Retriable
     ├─ 置 Connected（绿灯；v1.4 起绿灯=服务器侧监听已申请成功）
     ├─ 竞速区间之外 spawn 监听/分发任务（不变式 1）：
     │   v1.3: -L listener（现状）+ -D SOCKS listener（socks.rs）
     │   v1.4: + -R 推送连接分发任务（recv forward_rx）
     │   v1.5: + 断线信号聚合任务（任一跳 Drop→单点信号）
     └─ 清理：abort 全部 handle + disconnect（v1.4 先 cancel_tcpip_forward；
         v1.5 按链逆序 disconnect 全部跳）
```

## 2. 数据模型演进总表

`ForwardSpec` 三期演进出处的唯一权威（决策⑦：平铺三字段 + `kind`，serde default，Dynamic 占位空目标）：

```rust
// v1.3 起
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize, Default)]
#[serde(rename_all = "lowercase")]
pub enum ForwardKind { #[default] Local, Dynamic }   // v1.4 增 Remote

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ForwardSpec {
    pub local_port: u16,     // Local/Dynamic: 本地监听端口；Remote: 请求服务器监听的端口
    pub remote_host: String, // Local: 跳板侧目标主机；Dynamic: ""（占位）；Remote: 本地目标主机
    pub remote_port: u16,    // Local: 跳板侧目标端口；Dynamic: 0（占位）；Remote: 本地目标端口
    #[serde(default)]
    pub kind: ForwardKind,
    #[serde(default, skip_serializing_if = "Option::is_none")]   // v1.4 起
    pub remote_bind: Option<String>, // Remote 专属：服务器侧绑定地址；None = "localhost"
}
```

字段语义按 kind 翻转由辅助方法消化（占位值/语义反转不外泄到业务代码）：

| 辅助方法 | Local | Dynamic | Remote |
|---|---|---|---|
| `listen_port() -> u16` | 本地监听端口 | 本地监听端口 | 服务器侧监听端口 |
| `target() -> Option<(&str, u16)>` | 跳板侧目标 | `None`（握手动态定） | 本地目标 |
| `has_local_listener() -> bool`（v1.4 起） | true | true | false |

统一语义：一条规则 = 一个监听点 + 一个固定或动态目标；监听点在本地（L/D）或服务器侧（R）。

`TunnelConfig` 演进（v1.5）：

```rust
pub struct Hop { pub user: String, pub host: String, pub port: u16 }

pub struct TunnelConfig {
    // …现有字段不变…
    #[serde(default)]
    pub hops: Vec<Hop>,          // 权威来源；空 = 旧数据，加载时迁移
    // jump_user/jump_host/jump_port 保留为 serde 兼容镜像（读入旧文件、写出第一跳，
    // 供旧版应用回滚时读到单跳近似），运行时代码一律走 hops（见 §5.1）
}
```

`src/types.ts` 与 model.rs 逐字段同步：`ForwardKind = "local"|"dynamic"|"remote"`、`ForwardSpec.kind?`/`remote_bind?`、`Hop`/`TunnelConfig.hops?`（不变式 6，各期清单含此项）。

## 3. v1.3 详细设计（-D）

### 3.1 模型与序列化（A3）

- `ForwardSpec` 加 `kind`（`#[serde(default)]`）+ §2 辅助方法；`ForwardSpec::dynamic(local_port)` 构造函数统一占位值（`remote_host=""`、`remote_port=0`）。
- 三向兼容（决策⑦）：旧 JSON 无 kind 读为 Local；新版读旧导出文件同理；旧版读新 JSON 忽略未知 kind 字段、Dynamic 规则显示为一条目标为空的怪规则（可接受，见提案风险表）。
- 导出格式版本不升（`kind` 为 optional 字段，`read_import` 向后兼容无需变化）。

### 3.2 解析器（A4）

- `parser.rs` 的 `FLAGS_WITH_ARG` 已含 `'D'`，仅需在参数 match 加分支：
  - `'D' => forwards.push(parse_dynamic_spec(&arg)?)`。
- `parse_dynamic_spec(spec)`：支持 `-D 1080` / `-D1080` / `-D localhost:1080` / `-D [::1]:1080`。解析规则：`rfind(':')` 且后段可解析为 u16 → 前段为 bind 前缀（**忽略**，与 `-L` 四段式丢弃 bind 行为一致）；否则整体为端口。返回 `ForwardSpec::dynamic(port)`。
- 与 `-L` 混用：`forwards` Vec 自然容纳（一条隧道混合规则），与 ssh 一行多 flag 语义对齐。
- `forwards.is_empty()` 报错文案更新为提及 `-L/-D`（报错行为本身不变）。
- `-g`（bind_all）对 SOCKS 监听同样生效（复用现有 bind_addr 选择）。

### 3.3 SOCKS5 模块（新文件 `src-tauri/src/socks.rs`，A6）

手写最小实现（决策③），仅三块公开面：

1. **握手纯函数**（单测核心，无 IO）：
   - `parse_greeting(buf) -> Greeting`：`NeedMore | NoAcceptableAuth | Ready`。校验 VER=0x05、读 NMETHODS+METHODS；客户端方法集含 0x00（免认证）→ Ready，否则 NoAcceptableAuth。
   - `parse_request(buf) -> Request`：`NeedMore | Invalid(&'static str) | Ok(SocksRequest)`。解析 `VER CMD RSV ATYP DST.ADDR DST.PORT`；ATYP 1=IPv4（4 字节）、3=域名（1 字节长度 + 域名**原样保留**，不由本地解析）、4=IPv6（16 字节）。
   - `SocksRequest { command: SocksCommand, host: SocksHost, port: u16 }`；`SocksHost = V4(..) | Domain(String) | V6(..)`（`Display` 产出传给 direct-tcpip 的目标字符串，IPv6 用 `Ipv6Addr::to_string()`，域名原样）。
2. **回复构造纯函数**：`method_reply(acceptable: bool)`（`[05 00]` / `[05 FF]`）；`reply(rep: Reply, host/port 用全零 BND)`。`Reply` 常量覆盖 0x00/0x01/0x02/0x03/0x04/0x05/0x07/0x08。
   - BIND(0x02) / UDP ASSOCIATE(0x03) → 回 REP=0x07 command not supported 后关闭。
   - 通道打开失败映射：`russh_error_to_reply(&russh::Error) -> Reply`——可识别变体映射（如 RequestDenied → 0x02 not allowed），未识别 → 0x01 general failure 并 `tracing::warn` 记录原始错误（channel open 被拒的确切 Error 变体实施时核对，兜底分支保证任何形态都有可读回码）。
3. **serve 接入**（由 tunnel.rs 调用）：`serve_dynamic(listener: TcpListener, session, notify)`——accept 循环；每连接 `tokio::spawn`：循环凑字节调纯函数完成握手（读超时 10s，防只连不说的探测连接积压）→ `channel_open_direct_tcpip(host, port, "127.0.0.1", 0)`（持 session 锁仅覆盖 open 调用，与 -L 相同）→ 成功回 0x00 并 `copy_bidirectional(tcp, channel.into_stream())`；失败回映射错误码。通道打开失败同时 `notify.notify_one()`（与 -L 的 session_error 一致：会话死亡时叫醒隧道任务走重连）。

### 3.4 tunnel.rs 接入

- `connect_and_forward` 的 forwards 循环按 `kind` 分支：Local 走现状；Dynamic 走 `socks::serve_dynamic`（同样先 `TcpListener::bind`，失败 `ConnectError::Retriable`，与现状一致）。listener 任务生成位置保持在竞速区间之外、清理统一 abort（不变式 1，零变化）。
- `establish_session` 的 `:22` 二级登录预检条件改为 `forward.kind == Local && forward.remote_port == 22`（显式按 kind 判断，不依赖占位值碰巧不等）。

### 3.5 其余触点

- 前端：`TunnelEditor` 预览行 Dynamic 渲染「本地 :1080 → SOCKS 代理（跳板侧解析域名）」；`TunnelList`「目标」列 Dynamic 显示「SOCKS 代理」；`matchesQuery` 搜索字段跳过 Dynamic 的 `remote_host`/`remote_port`（空串/0 占位值无搜索意义，且 `"0"` 会误命中）。

## 4. v1.4 详细设计（-R，B1~B5 细化）

### 4.1 模型与序列化（B4）

- `ForwardKind` 增 `Remote`；`ForwardSpec` 增 `remote_bind: Option<String>`（serde default + skip_serializing_if，三向兼容同 §3.1 论证）。语义映射见 §2 表格。
- 构造函数 `ForwardSpec::remote(listen_port, target_host, target_port, bind: Option<String>)` 统一构造。
- 默认绑定：`remote_bind: None` → 申请时传 `"localhost"`（服务器 GatewayPorts=no 时等效回环，决策④安全默认；带 bind 前缀时原样传给 `tcpip_forward`，是否放行由服务器 GatewayPorts=clientspecified 决定，与 OpenSSH 行为一致）。

### 4.2 解析器（B4）

- `'R'` 分支 + `parse_remote_spec(spec)`：支持 `-R [bind:]port:host:port` 的 3 段与 4 段形态（沿 `parse_forward_spec` 的 splitn 思路），映射为 `ForwardSpec::remote(port, host, target_port, bind)`。
- IPv6 字面目标不支持（与现有 `-L` 支持度一致，`splitn` 会劈开方括号字面量），域名/IPv4 目标可用；此为与 `-L` 对齐的既有边界，非新增缺口。
- `-R 0:host:port` 解析为合法（local_port=0，服务器动态分配），运行时行为见待裁决项 1。

### 4.3 回调架构（SshClientHandler 扩展，B1 核心）

```rust
pub(crate) struct ForwardedConn {
    pub listen_addr: String, // 服务器回报的 connected_address = 我们申请时的 address
    pub listen_port: u16,    // connected_port，用于匹配回规则
    pub channel: russh::Channel<russh::client::Msg>,
}

pub(crate) struct SshClientHandler {
    disconnect_tx: Option<oneshot::Sender<()>>,          // 不变（Drop 断线信号语义不动）
    forward_tx: Option<mpsc::UnboundedSender<ForwardedConn>>, // v1.4；仅主跳 -R 连接携带
}
```

- `Handler::server_channel_open_forwarded_tcpip` 实现（查证签名见附录 A3）：回调里把 `ForwardedConn` 经 `forward_tx` 发出后**立即返回 Ok**。两条硬约束（源自附录 A4/A6 查证）：
  1. 回调运行在连接读循环任务里，**不得 await 长活**（会卡死整条 SSH 连接的消息处理）——用 Unbounded 通道立即转手；无背压风险可控（连接对象本身轻、断开即随 drop 释放），方案接受并注明。
  2. 回调返回 Err 会经 `?` 中断整个读循环——实现必须吞掉业务错误只返回 `Ok(())`。
- 通道在回调前已被 russh 自动 confirm（附录 A4）：无 receiver（本隧道无 -R 规则）时直接 drop channel，服务器侧该连接随即关闭，行为正确。
- `establish_session` 返回值从二元组改为 `EstablishedSession { handle, disconnect_rx, forward_rx: Option<Receiver<ForwardedConn>> }`；仅当 config 含 Remote 规则时创建通道对，`connect_jump_host` 的两阶段连接均携带同一 `forward_tx`（哪条连接认证成功哪条负责接收推送；失败的那条被替换丢弃，其 handler 的 forward_tx 发送目标相同，无歧义）。`setup_second_layer`/`open_target_session` 构造的 handler 一律 `forward_tx: None`。

### 4.4 connect_and_forward 接入（B1/B2、绿灯语义）

时序（严格顺序）：

1. `establish_session` 完成（竞速区间内，不变）。
2. **逐条 Remote 规则**：`session.tcpip_forward(bind_or_localhost, listen_port)`（外裹 `tokio::time::timeout(15s)`——russh 无内置超时，见附录 A7）。记录实际生效的 (address, port) 到本隧道的远端规则匹配表；`-R 0:` 申请成功时应答携带实际端口（附录 A2），经 `emit_notice` 展示（待裁决项 1 的最小形态）。
3. 全部申请成功 → 置 `Connected`（绿灯）。**绿灯 = 服务器已开始监听远端端口**（提案状态语义做实：申请失败时从未亮绿）。
4. 竞速区间外 spawn（不变式 1）：
   - `-L`/`-D` listener 任务（现状/§3.4）。
   - **-R 分发任务**：`loop { forward_rx.recv() }`；按 `(listen_addr, listen_port)` 匹配 Remote 规则取本地 `target()`；命中 → 每连接 spawn 泵任务（`TcpStream::connect(target)` → `copy_bidirectional(channel.into_stream(), tcp)`）；本地连不上 → drop channel（服务器侧连接关闭，发起方看到 connection refused）；不匹配（服务器配置漂移等）→ drop + `tracing::warn`。泵任务不阻塞分发循环。
5. 清理（select 退出后）：abort 分发任务与全部 listener handle → 逐条 `cancel_tcpip_forward(address, port)` → `session.disconnect(...)`（服务器侧监听随连接关闭必然撤销，cancel 只是显式收尾；顺序保证分发任务不再收到新连接）。
6. **B2 重连恢复**：`run_tunnel` 外层循环重跑 `connect_and_forward` → 重新 establish → 重新逐条 `tcpip_forward`，天然满足「重连成功后服务器侧监听自动恢复」，无需额外状态。

### 4.5 错误分类（B3）

查证事实（附录 A7）：服务器明确拒绝 → `russh::Error::RequestDenied`；会话任务已死（oneshot 断）→ `russh::Error::Disconnect`；无内置超时。分类设计：

| 形态 | 归类 | 用户可见 |
|---|---|---|
| `Error::RequestDenied` | `ConnectError::Fatal` | 「远端端口 {port} 被服务器拒绝（可能被占用或未开放转发），已停止」——红灯、不重连 |
| `Error::Disconnect` / 其他 russh 错误 | `ConnectError::Retriable` | 走既有退避重连（网络类） |
| 15s 超时 | `ConnectError::Retriable` | 「申请远端转发监听超时」——会话僵死按网络类处理 |

- Fatal 返回前先 `session.disconnect(...)` 显式收尾再 return（与 `:22` 预检失败路径同一模式，防 handler 任务残留到 keepalive 超时）。
- 分类逻辑写成独立函数 `classify_tcpip_forward_err(e) -> ConnectError` + 单测（B3 自动化：RequestDenied→Fatal 分支、Disconnect→Retriable 分支、超时→Retriable 分支）。
- 前端零额外改动：Fatal → `Failed(String)` → App.tsx 既有「非 Failed→Failed 跳变弹 banner」自动覆盖（CLAUDE.md banner 约定）。

### 4.6 probe / 杀端口按类型跳过（B5）

- `probe_forwards`：只遍历 `has_local_listener()` 的规则；隧道全部规则为 Remote → 返回 `Free`（无本地端口可探测，语义：不阻止应用自己连接）。
- `commands.rs` 的 `connect_tunnel` Broken 分支：`kill_port_listeners` 只对 `has_local_listener()` 的规则调用（远端端口是服务器上的进程，不能也不该 kill）。
- `detect_existing`/`mark_external`：全 Remote 隧道探测恒 Free → 不 mark_external、保持 Disconnected，由用户显式连接（应用无法感知外部 `ssh -R` 进程；此为 B5 语义内的已知限制：跳过即满足「不误杀、不误判」）。混合规则隧道（-L+-R）monitor 只看本地端口，外部 -R 部分失联检测不到——同上已知限制，方案注明不扩基线。

### 4.7 前端

- `TunnelList`：「监听端口」列 Remote 渲染「远端 :8080」（bind 非默认时附 bind）；「目标」列渲染本地目标 `host:port`；搜索字段按 kind 取有效字段。

## 5. v1.5 详细设计（-J，C1~C5 细化）

### 5.1 模型 hops 与存量迁移（C5）

- `Hop { user, host, port }`；`TunnelConfig.hops: Vec<Hop>`（`#[serde(default)]`）为**唯一权威来源**；`jump_user/jump_host/jump_port` 降级为 serde 兼容镜像：读入旧文件、序列化时双写第一跳（旧版应用回滚时按 legacy 三字段读到单跳近似，多跳信息丢失但列表完整——与决策⑦回滚哲学一致）。
- 迁移入口（store 加载路径）：`lib.rs` 在 `load_tunnels()` 后、`TunnelManager::new` 前调用 `migrate_hops(&mut tunnels)`（与 `migrate_env_case` 同一模式）：`hops.is_empty() && !jump_host.is_empty()` → 生成单跳；幂等（已迁移数据第二遍无变化）；有变化时回写 `save_tunnels`。运行时全部代码访问跳板信息一律走 `hops`（`first_hop()` 辅助方法供钥匙串等单跳场景），legacy 字段除 serde 外无读者。
- 钥匙串：命名 `user@host:port` 每跳天然不冲突（提案已核对），`store.rs` 函数签名不变，调用点从 `config.jump_*` 改为 `config.first_hop()` 对应字段。
- 导入导出：`hops` 为 optional 字段，旧导出文件读入后经同一迁移；`EXPORT_VERSION` 不升。多跳密码导出范围见待裁决项 2。
- C5 单测：旧三字段 JSON → load/migrate → `hops.len()==1` 字段无损；迁移幂等；新格式 roundtrip；legacy 双写断言（序列化结果同时含 hops 与第一跳 legacy 值）。

### 5.2 解析器（C4）

- `'J'` 分支 + `parse_jump_list(arg)`：逗号分隔，每项 `[user@]host[:port]`（复用 `parse_hostport`；`rfind('@')` 拆 user）。user 缺省继承 destination 的 user（OpenSSH 语义），port 缺省 22。
- `hops = J 列表 + [destination 一跳]`（destination 始终是最终跳）；`-J` 与 `-L/-D/-R` 自由组合。
- 目标机显示名生成（`display_name`）沿用第一跳 host。
- C4 单测：`ssh -J u1@h1:2222,u2@h2 -L ... u3@h3` 全形态（省 user、省 port、单项单跳）、`-J` 无 destination 报错。

### 5.3 嵌套链连接与每跳两阶段认证（C1、决策⑤⑥）

`establish_session` 重构为 `hops` 逐跳循环（沿用 `open_target_session` 已验证的「通道当网线」模式）：

```
prev = None
for (i, hop) in hops.iter().enumerate():
    handle = match prev:
        None => connect_jump_host(config_with_keepalive, hop)          // 第一跳：直连 TCP
        Some(prev) => open_hop_session(prev, hop)                       // 后续跳：direct-tcpip 通道
                    //   channel = prev.channel_open_direct_tcpip(hop.host, hop.port, "127.0.0.1", 0)
                    //   .into_stream() → russh::client::connect_stream(同一 keepalive Config, handler)
                    //   外裹 timeout(JUMP_CONNECT_TIMEOUT=15s)——现状 open_target_session 无超时，统一补上
    两阶段认证（复用现有函数，逐参传 hop）：
      phase1: open_hop_session 新通道（独立 MaxAuthTries 预算）逐 key 试 try_publickey_auth
      phase2: 再 open_hop_session 新通道走 password_phase（layer 带 hop 标注，§5.5）
    handle 存入 chain，prev = Some(handle)
:22 预检：只对最终转发目标执行（setup_second_layer 改用 chain 最后一跳的 handle；中间跳本身即 SSH 登录，无预检）
返回 EstablishedSession { chain: Vec<Handle>, disconnect_rx（聚合，§5.4）, forward_rx }
```

- 每跳 keepalive 独立：`connect_stream` 与第一跳共用同一 `Arc<Config>`（keepalive 15s / max 3，与现状主跳相同）——**必须**，否则中间跳死亡无法检测（C3 前提）；现状 `open_target_session` 用 `Config::default()`（无 keepalive）是一次性会话所以无碍，v1.5 起长连链一律带 keepalive。
- 「阶段二换一条全新连接」对中间跳的语义 = 经由同一前链再 open 一个 direct-tcpip 通道（不重连前面的跳）；每条通道是独立 SSH 连接，MaxAuthTries 预算独立，两阶段不变式保持。
- 连接与认证全程仍在 `connect_and_forward` 的 select 竞速区间内（可随时 Stop/Reconnect 打断，不变式继承）；所有 `tokio::spawn` 均在竞速区间外（§1 骨架）。
- 顺带收敛：phase1 公钥失败被 phase2 替换的连接、重构后不再需要的中间产物，统一显式 `disconnect` 后丢弃（现状 phase1 连接靠 keepalive 超时自灭，属既有小瑕疵；重构范围内顺手收敛，不改变外部行为）。

### 5.4 断线信号逐跳接力（C3）

- 每跳 `SshClientHandler` 各带独立 `disconnect_tx`（oneshot）；`EstablishedSession` 持有全部 rx。
- spawn 一个**信号聚合任务**（竞速区间外）：`forward_first_signal(rxs, aggregated_tx)`——任一跳 rx 触发即向 `aggregated_tx` 发一次并退出（oneshot 单发天然去重；多跳同时断只发一次）。`connect_and_forward` 的 select 监听聚合信号，语义与现状单跳 `disconnect_rx` 完全一致（`Retriable("SSH session closed")`）。
- 无泄漏论证：Stop/清理路径显式 disconnect 最终跳 → 前链通道流断 → 各跳连接任务退出 → handler Drop → rx 触发 → 聚合任务发出（无人接收）后自然退出；正常断线路径同理。清理顺序（§1 骨架）：abort 监听/分发/聚合相关 handle → **按链逆序**逐跳 `disconnect`（先断最远跳，避免前跳替后跳产生误导性错误日志）。
- C3 作证：代码审读（聚合任务 + 每跳 handler Drop 语义，附录 A5）+ 人工终验（断开中间跳→黄灯 Reconnecting→恢复后可用；断第一跳同理）。

### 5.5 认证失败文案与密码弹窗标注（C2）

- 文案构造提为纯函数 `hop_auth_failure_msg(hop_index, hop_total, user, host) -> String` + 单测（C2 自动化「文案构造」）：多跳时「第 {n}/{total} 跳 {user}@{host} 认证失败（用户名或密码错误）」；**单跳（hops.len()==1）保持现有文案格式**（「跳板机 {user}@{host} 认证失败…」），存量用户零文案回归（A5 兼容）。
- `password_phase` 的 `layer` 参数扩展携带 hop 上下文；`tunnel://password-required` payload 增可选字段 `hopIndex`/`hopTotal`（`types.ts`/`api.ts` 同步）；`PasswordModal` 多跳时标题渲染「第 N/M 跳 · {host}」，单跳与 target 层维持现状文案。弹窗取消语义不变（取消 = disconnectTunnel，不变式 3）。

### 5.6 其余触点

- `-R` 与 `-J` 组合：tcpip_forward / forwarded-tcpip 回调挂在**最终跳** handle 上（附录 A1/A3 为 Handle/Handler 通用能力，天然支持）。
- `probe`/`detect_existing`/`mark_external`：与跳数无关（探测本地端口），v1.5 零改动。
- 前端：`TunnelList`「跳板机」列多跳渲染「h1 → h2 → h3」（各跳附非 22 端口）；`TunnelEditor` 预览显示链路各行。
- store 钥匙串调用点、`transfer.rs` 的 `jump_user/jump_host/jump_port` 引用改走 `first_hop()`/hops。

## 10. 待裁决项

| # | 事项 | 推荐 | 理由与代价 |
|---|---|---|---|
| 1 | `-R 0:target` 动态端口的呈现深度（提案 §3.2「可选小项：回填 UI」与本方案最小形态有差距） | 最小形态：解析合法 + 申请成功后 `emit_notice` 显示实际端口（附录 A1/A7 已证实应答携带端口）；列表常驻展示运行时端口**不做** | 常驻回填需引入「运行时端口 ≠ 配置端口」的状态通道与渲染，且重启后重新分配端口会漂移，UI 误导风险大于收益；notice 已满足「能知道连哪」的最小诉求。代价：用户须从通知里记端口 |
| 2 | v1.5 导出文件是否携带多跳全部密码 | **推荐顺带扩展**：`TunnelSecret` 增可选 `hop_passwords: Vec<Option<String>>`（按 hops 顺序，serde default，格式版本不升），导入侧仅写 Some | 导出/导入是回滚与迁移的兜底手段（提案风险表）；多跳密码不导出会让中间跳凭据在换机/恢复场景全部丢失，兜底价值减半。代价：v1.5 清单 +1 项（transfer.rs 两处），复杂度小 |
| 3 | hops 与 legacy 三字段双写（提案说「重构」，本方案保留 legacy 作 serde 镜像） | 保留双写（hops 为唯一权威，legacy 仅 serde 层读写第一跳） | 让旧版应用回滚后仍能读到单跳近似（列表不坏），与决策⑦的回滚哲学一致；代价是 model 多三个 deprecated 字段、序列化体积略增。若裁决不要回滚兼容，可改为纯 hops + 迁移时丢弃旧字段，实现更净 |
