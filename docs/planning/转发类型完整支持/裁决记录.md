## 提案决策①「分三期交付」 — 偏离（执行形式细化）

1. **问题证据**：提案 §3.0/§5 决策①原文「分三期 = 三轮完整发布流程（含打 tag，见项目 CLAUDE.md 发布规范）」；阶段 0 用户选择「三期连做」，与「三次独立交付会话」的字面理解存在出入。
2. **备选方案**：
   - a. 三次独立 pipeline 会话逐期执行——完全贴合提案字面，但用户已明确选择连做，且每次合并/发布都是强制停等，与用户意图相悖；
   - b. 一次 pipeline 内按期滚动：交付内核不变（三个独立版本号、独立验证、独立回滚点、commit 分层），发布动作统一收口到终态合并询问；
   - c. v1.3 完成后停下来问是否继续——违背「需求冻结后不停等」。
3. **裁决**：选 b。
4. **理由**：提案分期的核心价值是回归风险控制与可回滚性，方案 b 完整保留；「三轮发布流程」中的人工步骤（合并、打 tag、Releases 页面点 Publish）本来就必须人类参与，统一收口反而减少打断次数；每期实施前仍强制先有该期实施计划，满足提案「实施前需补充细节章节」约定。
5. **影响**：基线 §0 按此表述；终态合并询问需一并处理三个版本的发布事宜；二三期实施计划改为滚动产出（前一期评审通过后续跑 plan agent）。

## 方案待裁决项 1「-R 0: 动态端口呈现」 — 新增（采纳最小形态）

1. **问题证据**：实现方案 §10-1；提案 §3.2 原文「可选小项（倾向支持）：`-R 0:host:port` 动态分配端口……把实际端口回填 UI」与方案的最小形态（仅 notice 显示）存在差距。
2. **备选方案**：a. 常驻回填（列表显示运行时实际端口）；b. 最小形态 notice；c. 完全不支持 `-R 0:`。
3. **裁决**：b。
4. **理由**：常驻回填需引入「运行时端口 ≠ 配置端口」的状态通道与渲染，且重连后服务器可能重新分配导致端口漂移，UI 误导风险大于收益；notice 已满足「能知道连哪个端口」的最小诉求；API 附录 A1/A7 证实应答携带实际端口（主控已独立抽查证实），实现代价小。
5. **影响**：v1.4 清单不变（emit_notice 已含）；提案「倾向支持回填 UI」降级为最小形态，终态汇报列入说明。

## 方案待裁决项 2「v1.5 导出携带多跳密码」 — 新增（采纳扩展）

1. **问题证据**：实现方案 §10-2；基线与提案均未约定多跳密码的导出范围（提案 §3.3 仅说钥匙串 `user@host:port` 天然不冲突，未覆盖导出文件）。
2. **备选方案**：a. 不扩展（多跳密码不随导出携带）；b. `TunnelSecret` 增可选 `hop_passwords: Vec<Option<String>>`。
3. **裁决**：b。
4. **理由**：导出/导入是换机与恢复场景的兜底手段（提案 §6 风险表）；多跳密码不导出会让中间跳凭据在恢复场景全部丢失，兜底价值减半；optional 字段格式版本不升，复杂度小。
5. **影响**：v1.5 清单 +1 项（transfer.rs 两处）；导出文件含明文密码沿用 v1.2 既有安全模型，无新增暴露面。

## 评审 S1「SOCKS 单条目标失败误断整条隧道」 — 改写（打回修正）

1. **问题证据**：评审报告 §1.1（S1）——`socks.rs:336-342` 对 `channel_open_direct_tcpip` 失败无条件 `notify_one()`；`tunnel.rs:319` 将其翻译为 `ConnectError::Retriable("SSH channel error")`，随即中止全部监听、断开会话、进入退避重连；`auto_reconnect=false` 时直接红灯。russh 0.44.1 将服务端 CHANNEL_OPEN_FAILURE（目标拒绝/不可达）映射为 `Error::ChannelOpenFailure(_)`，此时会话健康；真正的会话死亡已有 `SshClientHandler::Drop → disconnect_rx`（`tunnel.rs:26-38/315-317`）独立覆盖。该写法忠实执行了《实现方案》§3.3，属**方案层缺陷**。
2. **备选方案**：a. 仅对会话级错误（Disconnect/SendError/HUP 等）通知；b. SOCKS 侧完全移除 `notify_one()`，依赖既有 `disconnect_rx`；c. 维持现状（否决——真实多目标负载下代理会反复自断）。
3. **裁决**：b，并把「错误 → 是否通知会话死亡」抽成纯函数 + 单测，锁住「目标级失败 ≠ 会话死亡」语义。
4. **理由**：会话死亡信号已由 handler Drop 覆盖，SOCKS 侧通知纯属重复且分类错误；方案 §3.3 的「open 失败同时 notify」是从 -L 旧路径照搬的错误类比（-L 路径的同类问题属既有行为，A5 零回归约束下本期不动）。纯函数 + 单测可防止 v1.4 `-R` 复制同一模式。
5. **影响**：socks.rs 修改 + 单测 + 变更摘要补记；方案 §3.3 该表述失效（以本条为准）；评审需复检。

## 实施计划 v1.3 偏离（4 项） — 新增（实施级细化，接受）

1. **问题证据**：变更摘要 §3 列 4 项偏离——①步骤 3 `mod socks;` 改为 `pub mod socks;`（非测试构建仍有 13 条 dead_code，测试引用不计入可达性）；②步骤 5 顺带移除 model.rs `listen_port()` 的过时 `#[allow(dead_code)]`；③russh 错误码按语义细分映射（计划仅要求可识别+兜底）；④握手超时改为 greeting+request 共用 10s 绝对 deadline 并按 `2+NMETHODS` 精确丢弃 greeting 前缀（兼容管线化客户端）。偏离 ① 超出实施计划「lib.rs 仅增一行 mod 声明」的字面写法。
2. **备选方案**：a. 全部打回严格按计划（含临时 `#[allow(dead_code)]`）；b. 接受偏离并逐条入账；c. 只打回偏离 ①。
3. **裁决**：b（偏离 ① 的模块可见性交评审给出独立意见后再定）。
4. **理由**：项目铁律「零警告」，`pub mod` 是消除 dead_code 的最干净解法且行为零变化；偏离 ② 属过时抑制清理（同文件、零行为）；③④ 均在计划授权的「可识别映射+兜底」「读超时防积压」范围内细化，且单测全覆盖。打回仅换来形式一致，收益不足以抵消返工与临时 allow 的技术债。
5. **影响**：SOCKS 模块成为 crate 公共项（无外部消费者，无实际暴露风险）；评审报告需对偏离 ① 给出意见，若评审提出实质问题则打回修正。

## 基线不变式 4「本地 cargo 验证」 — 偏离（环境配置方案，用户授权）

1. **问题证据**：基线 §2.4 不变式 4 要求每期收口本地跑 `cargo build`/`cargo test`；事实为本机无 Rust 工具链（`cargo` command not found、`~/.cargo` 不存在、主工作区无 target 目录）且仓库无 push/PR CI（`.github/workflows/` 仅 tag 触发的 release.yml）。
2. **备选方案**：a. 安装 rustup + 项目级 `rust-toolchain.toml` + 新增 CI workflow；b. 只装 rustup 不加 CI；c. 不装本地，验证全靠远端（但远端亦无可用 CI，等价于无验证）。
3. **裁决**：选 a。用户授权原文：「使用 rust 的安装配置为这个项目配置本地开发环境，如果没有的话，你需要遵照惯例，需要有 rust 的版本管理器，并且使用管理器为本项目安装环境；同时需要 ci workflow，这个很重要，可以同时创建脚本」。
4. **理由**：cortex 检索确认知识库无 rust-env 条目（有 java(SDKMAN)/go(toolchain)/python(uv)/nodejs(Volta) 的「版本管理器 + 项目级固定文件」惯例）；rustup + `rust-toolchain.toml`(1.100.0) 与该惯例一致；本地（rustup）+ 远端（CI push/PR 触发）双重闭环后基线不变式 4 完整可执行。依据不足处：无。
5. **影响**：`rust-toolchain.toml`、`.github/workflows/ci.yml`、`scripts/ci.sh` 为新增仓库文件（随 pipeline 提交）；rust-toolchain.toml 由主控作为环境准备落盘，ci.yml/scripts 由 subagent 独立 commit；终态汇报时提议将 rust-env 知识沉淀入 cortex（store 需用户确认，届时出预览）。
