## 1. 问题清单（按严重度排序）

### 1.1 严重（1 项）

#### S1：SOCKS 单条目标不可达被误判为「会话死亡」，会杀掉整条隧道（重连或直接红灯）

**证据链**

1. `src-tauri/src/socks.rs:336-342`：`channel_open_direct_tcpip` 失败后，除回写 SOCKS 错误码外，无条件执行 `session_error.notify_one()`。
2. `src-tauri/src/tunnel.rs:319`：该通知在竞速 select 中被翻译成 `Err(ConnectError::Retriable("SSH channel error"))`；随后 `tunnel.rs:323-325` 中止全部 listener、断开 SSH 会话，`run_tunnel`（`tunnel.rs:136-160`）进入退避重连；若该隧道 `auto_reconnect == false`，则直接置 `Failed`（红灯）并停止。
3. 触发这一错误分支的，不只有「会话死亡」：russh 0.44.1 把服务端返回的 `CHANNEL_OPEN_FAILURE` 映射为 `Err(Error::ChannelOpenFailure(reason))`（`~/.cargo/registry/src/*/russh-0.44.1/src/client/mod.rs:441-442`）。服务端在**目标端口拒绝连接 / 目标不可达**时正是回 `SSH_OPEN_CONNECT_FAILED`（已由 `socks.rs:199-205` 映射成 SOCKS 0x05），此时 SSH 会话本身完全健康。
4. 真正的会话死亡已有独立信号：`SshClientHandler::Drop`（`tunnel.rs:26-38`）关闭 oneshot，`tunnel.rs:315-317` 的 `drx` 分支负责重连。因此 SOCKS 侧的 `notify_one()` 不是检测会话死亡所必需的。

**影响**

- SOCKS 代理的典型负载（浏览器、IDE、curl 探测）天然包含大量「目标拒绝/域名解析失败/端口不可达」的请求。任意一条失败都会：拆掉全部 `-L` 与 `-D` 监听、打断其他正在传输的连接、重新走完整认证（密码认证的跳板机会再次弹密码框）、甚至把整条隧道永久打成红灯（关闭自动重连时）。
- 这意味着 A1/A2 即使在「目标可达」的演示路径上通过，实际代理使用体验也会被单条失败请求反复打断。

**定性**：实现忠实执行了《实现方案》§3.3 的写法，属于**方案层缺陷**而非实现走样；但它是本期唯一会直接伤害用户的功能性问题，且修复面很小。

**建议修复（评审未改代码）**

- `socks.rs` 仅对「会话级错误」发通知（`Error::Disconnect` / `Error::SendError` / `HUP` 等），对 `Error::ChannelOpenFailure(_)` 只回 SOCKS 映射码、不发通知；更简单的做法是 SOCKS 路径完全去掉 `notify_one()`，依赖 `disconnect_rx` 覆盖会话死亡。
- 给该分类逻辑抽一个纯函数并补单测，锁住「目标级失败 ≠ 会话死亡」这一语义。
- 该问题应在 v1.4（`-R` 会引入更多 channel 操作）之前修掉，避免同一模式扩散。

### 1.2 中等（1 项，既有问题，非本期引入）

#### M1：多规则隧道中「前序 listener 已启动、后续 bind 失败」会泄漏 listener，导致永久重连

**证据**

- `tunnel.rs:230-308`：每条规则 `TcpListener::bind(...)?` 失败即从 `connect_and_forward` 提前返回；`listener_handles` 是函数局部 `Vec`，提前返回时 `JoinHandle` 被直接 drop（detach），仅在正常清理路径 `tunnel.rs:323-325` 才 `abort()`。先启动的 listener 任务继续 accept 并占住端口。
- `probe.rs:49-67`：`probe_forwards` 在**任一**端口为 Free 时立刻返回 `Free`，因此启动前预检并不保证「所有规则端口都可绑」。
- 后果：后续轮次在第一条规则上就会 `Cannot bind ... Address already in use`（占用者就是自己上一次泄漏的任务），退避重连永远失败。

**范围判定**：多 `-L` 规则下早已存在，v1.3 未引入；混合 `-L`/`-D` 规则让触发面略微变大。与评审重点「`-D` 与 `-L` 混排的 bind 冲突处理」一致——处理方式与 `-L` 完全相同，未出现新的不一致。**不阻塞本期**，建议 v1.4 前在错误路径上 abort 已注册的 handle。

## 6. 最终结论

**有条件通过。**

条件（须在本期收口前处理）：

1. **修复 S1**：SOCKS 的单条目标失败（`russh::Error::ChannelOpenFailure(_)` 等目标级错误）不得触发 `session_error`，从而不得拆掉整条隧道/引发重连或红灯。建议仅对会话级错误（`Disconnect`/`SendError`/`HUP` 等）发通知，或直接删掉 SOCKS 路径的 `notify_one()` 并依赖既有 `disconnect_rx`；补一条分类单测。
2. **人工终验 A1/A2/A4/A5**：由用户在真实跳板机环境执行（终验清单见《变更摘要》§4），A1 建议额外观察「一次目标拒绝后隧道是否保持在线」，这正是 S1 的用户可见面。

非阻塞项：M1（多规则部分 bind 失败的 listener 泄漏）与 L1~L8 记入遗留清单，建议 v1.4 前处理 M1 与 L8。

在 S1 未修复前，自动化验证虽全绿（tsc 0 / build 0 警告 / 30 测试连续两次全绿），但 SOCKS 代理在真实多目标负载下会反复自断，不建议按当前形态对外发布 v1.3.0。

### 7.2 S1 闭合判断：**已闭合**

逐一排查「目标级失败仍能触发整条隧道重连/红灯」的全部可能路径：

1. **SOCKS 通道打开失败**：唯一通知点在 `socks.rs:383`，现已由 `classify_channel_error` 门控；`ChannelOpenFailure::ConnectFailed/AdministrativelyProhibited/ResourceShortage/UnknownChannelType/Unknown` 全部判为 Target，只回映射码并关闭该请求任务。
2. **打开成功后的数据面错误**：`copy_bidirectional` 错误只记 debug（`socks.rs` 成功分支），从不 notify。
3. **握手失败/超时/客户端提前关闭**：仅返回错误由 spawn 包装层记 debug，从不 notify。
4. **accept 错误**：仅 break 该 listener，从不 notify。
5. **`russh_error_to_reply`**：纯映射，无副作用。
6. **全仓 notify 调用点**：`grep -rn "notify_one|notify_waiters|.notify("` 仅命中 `tunnel.rs:281`（-L，既有、主控裁决明确不动）与 `socks.rs:383`（已门控），无其他任务内的隐藏唤醒点。
7. **session 锁中毒**：会话锁是 `tokio::sync::Mutex`，无中毒语义；`std::sync::Mutex` 只用于 `password_senders`，不在 SOCKS 路径。客户端任务 panic 不会污染会话或隧道状态。

**「未识别错误默认 Target」是否引入「会话真死却无人唤醒」缺口：无实质缺口。**

- `channel_open_direct_tcpip` 在 russh 0.44.1 中只会产生三种错误形态：命令通道关闭 → `SendError`（`client/mod.rs:513-523` 的 `map_err`）、服务端拒绝 → `ChannelOpenFailure(reason)`（`client/mod.rs:441-442`）、确认发送端关闭 → `Disconnect`（`client/mod.rs:444-446`）。真正代表会话死亡的两类（`SendError`/`Disconnect`）都已归入 Session；默认分支实际只会被本调用路径产不出的变体命中（防御性兜底）。
- 即便分类漏判，会话死亡仍有独立兜底：`SshClientHandler::Drop`（`tunnel.rs:26-38`）关闭 oneshot → `drx` 分支（`tunnel.rs:315-317`）→ `Retriable` 重连；TCP 黑洞由 keepalive（15s×3）兜底。
- 取舍方向正确：误唤醒会杀掉健康隧道，漏唤醒有 Drop 兜底。
