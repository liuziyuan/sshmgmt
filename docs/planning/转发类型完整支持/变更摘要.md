### 执行中偏离及原因

1. **步骤 3：`mod socks;` → `pub mod socks;`**。实施计划预期「纯函数全部被单测引用，无 dead_code」；实测非测试构建仍报 13 条 dead_code 警告（`#[cfg(test)]` 引用不计入非 test 构建的可达性分析）。改为在 crate 根声明 `pub mod socks;`，使纯函数成为 crate 公共项、零警告且无需临时 `#[allow(dead_code)]`；步骤 4 接线后未回收（模块无外部消费者，公开无害）。lib.rs 仍只增一行，与计划「增一行模块声明」等价。**评审后已按 L2 收敛为 `pub(crate) mod socks;` + 4 个定向 allow，见 §5。**
2. **步骤 5 顺带移除过时抑制**：`model.rs` 中 `listen_port()` 的 `#[allow(dead_code)]` 及其「probe 步骤 5 接线」注释已过时（步骤 4 起 tunnel.rs 已调用），随本步移除；行为零变化。`target()` 的 `#[allow(dead_code)]` 保留（v1.3 无调用方，v1.4 dispatch 才使用）。
3. **russh 错误码映射细化**：计划仅要求「可识别变体映射 + 未识别兜底 0x01」。实作按语义映射：`RequestDenied` / `AdministrativelyProhibited` → 0x02，`ConnectFailed` → 0x05，`UnknownChannelType` → 0x07，`ResourceShortage` / `Unknown` → 0x01，其余变体 → 0x01 + `tracing::warn` 原始错误。全部由单测覆盖。
4. **握手超时语义**：采用「greeting + request 共用一个 10s 绝对 deadline」，而非每次 read 各 10s，避免慢速滴流连接无限占用任务；请求前一个 read 可能同时带回 greeting 与 request 字节，按 `2 + NMETHODS` 精确丢弃 greeting 前缀而非清空整个缓冲区，兼容管线化客户端。

## 4. 遗留风险与人工终验清单

**遗留风险**

- SOCKS5 仅实现 CONNECT + 免认证：需要用户名/密码认证或 UDP ASSOCIATE 的客户端会被拒绝（0xFF / 0x07），属方案锁定的最小实现范围。
- 握手阶段客户端若在 10s 内未完成 greeting+request（极高延迟或异常客户端）会被断开；探测型连接不再无限占任务。
- SOCKS 监听与 -L 监听共用 accept 循环失败处理：listener 永久性 accept 错误会结束该监听任务（与现状 -L 一致），隧道本身仍由断线信号驱动重连。
- 无 SOCKS over 真实 SSH 会话的自动化集成测试（需真实跳板机，基线 §5 禁止）→ A1/A2/A4 依赖人工终验。
- `-g` 时 SOCKS 端口绑定 0.0.0.0，与 -L 行为一致；这是现有语义，非本次新增风险。
- 旧版应用回滚读取新配置时，Dynamic 规则会显示为 remote_host 为空的普通规则（决策⑦已接受的兼容性代价）；前端 `kind` 声明为必填，但运行时缺失值会落入 Local 渲染分支，不会崩溃。

**人工终验清单（由用户真实跳板机执行）**

- A1：`curl --socks5-hostname 127.0.0.1:<D端口> http://<内网域名>/`（验证跳板侧域名解析）；另测 IP 目标。
- A2：连接中杀掉跳板侧会话/断网 → 观察退避重连 → 恢复后同一 curl 再通。
- A4：粘贴 `ssh -L 10008:host:3306 -D 1080 user@jump` 建隧道，两种转发同时工作。
- A5 抽查：两阶段认证、密码错误红灯、连接中（黄灯）点断开立即生效、`:22` 预检、公钥上传各一次。

## 5. 评审修正（第 1 轮，commit `0b7db91`）

> **《实现方案》§3.3 中「通道打开失败同时 notify.notify_one()（与 -L 的 session_error 一致）」的表述已失效，以本节修正为准。** 该写法源自方案层缺陷（评审 S1）：服务端 `CHANNEL_OPEN_FAILURE` 表示该目标拒绝/不可达，SSH 会话本身健康；无条件 notify 会被 tunnel.rs 翻译成 Retriable 并拆掉整条隧道（自动重连关闭时直接红灯）。

### S1 修复点与语义

- `socks.rs` 新增纯函数 `classify_channel_error(&russh::Error) -> ChannelErrorKind`：
  - `ChannelErrorKind::Session`：仅 `Disconnect` / `SendError` / `HUP` 三个明确会话级变体（russh 0.44.1 中 `channel_open_direct_tcpip` 实际可达的会话级错误为前两者；`HUP` 为防御性覆盖）。
  - `ChannelErrorKind::Target`：`ChannelOpenFailure(_)`（服务端拒绝该目标）以及所有未识别变体。
- `handle_client` 失败分支：先回 SOCKS 映射错误码并记日志；仅当分类为 `Session` 才 `session_error.notify_one()`，`Target` 只让本次 SOCKS 请求失败，隧道与其它监听不受影响。
- 未识别错误默认 `Target` 的理由：真实会话死亡已由 `SshClientHandler::Drop → disconnect_rx` 独立覆盖，漏一次唤醒不会漏掉死会话；而误唤醒会杀掉健康隧道。两类错误的不对称代价决定默认值。
- `-L` 路径的既有 notify 行为未改动（评审明确要求）。

### L2 可见性收敛

- `lib.rs`：`pub mod socks;` → `pub(crate) mod socks;`，模块不再是 crate 公开 API。
- `socks.rs` 的 `Reply` 中 4 个无构造方的协议变体 `NetworkUnreachable` / `HostUnreachable` / `TtlExpired` / `AddressTypeNotSupported` 各加定向 `#[allow(dead_code)]` 并注明保留原因（对齐 RFC 1928 协议面）；其余项不加 allow。
