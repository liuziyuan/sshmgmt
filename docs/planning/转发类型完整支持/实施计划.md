## 2. 执行步骤（按依赖排序，每步收口编译/测试绿）

统一验证前缀：Rust 命令在 `src-tauri/` 下执行（`cd src-tauri && cargo …`，cargo 按环境注记获取）；前端命令在仓库根执行。

### 步骤 1：model.rs 类型与辅助方法（+ 构造点机械修补）

- 动 `model.rs`：新增 `ForwardKind`（`Local`/`Dynamic`，`#[serde(rename_all = "lowercase")]`、`Default = Local`、derive `PartialEq/Eq/Copy` 备 tunnel 分支与测试断言用）；`ForwardSpec` 增 `#[serde(default)] pub kind: ForwardKind`；辅助方法 `listen_port()`、`target() -> Option<(&str, u16)>`、构造函数 `ForwardSpec::dynamic(local_port: u16)`（占位 `remote_host=""`/`remote_port=0`）；新增 `#[cfg(test)] mod tests`。
- 动 `parser.rs`（仅构造点）：`parse_forward_spec` 两处 `ForwardSpec { … }` 字面量补 `kind: ForwardKind::Local`。
- 动 `transfer.rs`（仅测试构造点）：`tests::config()` 的字面量补同字段。
- 行为变化：仅序列化兼容——旧 JSON 无 kind 读为 Local；其余零行为变化。
- 验证：`cargo test`（新增 model 兼容测试 passed，既有 10+6 测试全绿）；`cargo build` 零新警告。
- 完成判定：`cargo test` 输现新测试名（如 `model::tests::legacy_json_without_kind_reads_local`）passed；`target()`/`listen_port()`/`dynamic()` 各至少一条断言。

### 步骤 2：parser.rs `-D` 解析分支

- 动 `parser.rs`：参数 match 加 `'D' => forwards.push(parse_dynamic_spec(&arg)?)`；新增 `parse_dynamic_spec(spec: &str) -> Result<ForwardSpec>`（`rfind(':')` 后段可解析 u16 → 前段 bind 忽略；否则整体为端口；产出 `ForwardSpec::dynamic(port)`）；`forwards.is_empty()` 报错文案改为同时提及 `-L/-D`。
- 新增测试（`parser::tests`）：`-D 1080`、`-D1080` 连写、`-D localhost:1080`（bind 忽略）、`-D [::1]:1080`（bind 忽略）、混合命令 `ssh -L 10008:host:3306 -D 1080 user@jump`（两条规则、kind 断言、占位字段断言）、`-D` 坏形态报错（非数字端口）。
- 行为变化：`-D` 从静默吞掉变为生成 Dynamic 规则；空规则集报错文案变化（无既有测试依赖该文案）。
- 验证：`cargo test`。
- 完成判定：新增 parser 测试全部 passed（A4 自动化落点）；`cargo build` 零新警告。

### 步骤 3：socks.rs 握手/回复纯函数 + 单测（不接线）

- 新增 `src-tauri/src/socks.rs` + `lib.rs` 增 `mod socks;`。
- 本步只写纯函数（无 IO、无 tunnel 依赖）：`parse_greeting`、`parse_request`（返回 `NeedMore/Invalid/Ok(SocksRequest)`，ATYP 1/3/4，域名原样保留）、`method_reply`、`reply`（REP 常量 0x00/01/02/03/04/05/07/08）、`russh_error_to_reply`（可识别变体映射、未识别兜底 0x01）、`SocksHost` 的 `Display`（IPv6 用 `Ipv6Addr::to_string()`）。
- 新增 `#[cfg(test)] mod tests`：greeting 各 method 集（含/不含 0x00）、request 三种 ATYP、短包 NeedMore、坏 VER Invalid、BIND/UDP 请求解析为对应 command（供上层拒绝）、错误码映射函数各分支。
- 行为变化：无（新模块，无调用方；纯函数全部被单测引用，无 dead_code）。
- 验证：`cargo test`；`cargo build` 零新警告（重点核 dead_code）。
- 完成判定：socks 测试全 passed（A6 自动化落点）。

### 步骤 4：tunnel.rs 接线 + serve_dynamic

- 动 `socks.rs`：新增 `serve_dynamic(listener, session: Arc<TokioMutex<Handle<..>>>, notify)`——accept 循环 + 每连接 `tokio::spawn`（握手读超时 10s → `channel_open_direct_tcpip` → 成功回 0x00 + `copy_bidirectional`，失败回映射码；open 失败 `notify.notify_one()`）。签名泛型 `H: russh::client::Handler` 以避免对 tunnel.rs 的模块耦合。
- 动 `tunnel.rs` `connect_and_forward`：forwards 循环按 `forward.kind` 分支——Local 保持现状代码不动；Dynamic 分支 bind（`bind_all` 逻辑复用）后 `tokio::spawn` `serve_dynamic`，handle 推入既有 `listener_handles`。
- 动 `tunnel.rs` `establish_session`：`:22` 预检条件加 kind 判断（§1 第 2 行）。
- 行为变化：Dynamic 规则获得本地 SOCKS5 监听；Local 路径代码零改动。
- 验证：`cargo build`（tunnel.rs 零警告）；`cargo test` 全绿。
- 完成判定：build 输出无任何 warning；A1/A2 进入人工终验清单（§5）。

### 步骤 5：probe.rs 辅助方法替换

### 6.1 关键时序与实现约束（来自方案 §4，逐条落到步骤）

```
run_tunnel 外层循环（零改动）
 └─ connect_and_forward
     ├─ 全不可用规则守卫（Fatal）
     ├─ select! 竞速区间（结构零改动）
     │   └─ establish_session → EstablishedSession{handle, disconnect_rx, forward_rx}
     ├─ 逐条 Remote：tcpip_forward（15s 超时）
     │     └─ 失败：cancel 已申请 → disconnect → 分类返回（Fatal/Retriable）
     ├─ 置 Connected（绿灯 = 服务器侧监听已申请成功）
     ├─ 竞速区间外 spawn：-L/-D listener + -R 分发任务（TaskSet 托管，不进竞速）
     └─ 清理：abort 任务 → cancel_tcpip_forward → disconnect
```

1. **申请时序严格**：`establish_session` 成功 → 逐条 `tcpip_forward` → 全部成功才置 `Connected`。申请失败时从未亮绿。
2. **失败分类**（`classify_tcpip_forward_err`）：服务器明确拒绝 `RequestDenied` → `Fatal`，文案「远端端口 {port} 被服务器拒绝（可能被占用或未开放转发），已停止」；`Disconnect` / 其他 russh 错误 → `Retriable`；15s 超时 → `Retriable`，文案「申请远端转发监听超时」。**Fatal 前先 `disconnect` 收尾**（与 `:22` 预检失败同模式），防 handler 任务残留。
3. **回调不阻塞读循环**：`server_channel_open_forwarded_tcpip` 只做 `unbounded_send` 后立即 `Ok(())`；无 receiver 时 drop channel。回调返回 `Err` 会经 `?` 中断整条连接读循环（附录 A4），**实现上禁止向回调传播任何错误**。
4. **分发匹配**：按 `(connected_address, connected_port)` 精确匹配申请时记录的路由；未命中（服务器地址规范化等漂移）只 `warn` + drop，不做猜测性路由，避免把连接泵到错误目标。
5. **清理顺序**：先 abort 分发/listener 任务（不再收新连接）→ 逐条 `cancel_tcpip_forward`（**用实际生效端口**，`-R 0:` 尤其如此）→ `disconnect`。cancel 失败只记日志，服务器侧监听随连接关闭必然撤销。
6. **`-R 0:` 动态端口**：解析合法；申请成功以应答端口作为实际端口参与匹配与 cancel；全部规则申请成功后经 `emit_notice(..., "success", ...)` 统一显示「服务器已分配远端端口 {addr}:{port}」（裁决：不做列表常驻回填；先暂存后统一提示，避免中途失败时误导）。重连后端口可能变化，重新申请时会再次提示。
7. **Remote 不参与 `:22` 预检**：只有 Local 规则有固定跳板侧目标；Remote 的目标是本机服务，登录预检无意义（现有 `kind != Local` 守卫已覆盖，零改动）。
8. **probe / kill / detect_existing**：只处理 `has_local_listener()` 的规则。全 Remote 隧道恒 `Free` → 不 `mark_external`、不 kill、由用户显式连接。**已知限制（写入终态汇报）**：应用无法感知外部 `ssh -R` 进程；混合隧道的外部 -R 部分失联检测不到。跳过即满足 B5「不误杀、不误判」。
9. **`-g` 不影响 -R**：`bind_all` 只决定本地监听地址（-L/-D），Remote 的服务器侧绑定地址仅由 `remote_bind` 决定（None → 传 `"localhost"`，Some → 原样传，空串按 OpenSSH 语义即全接口）。
10. **已知取舍（保持方案时序）**：`tcpip_forward` 申请在竞速区间之外执行，申请期间不轮询 `control_rx`，Stop 最坏延后「15s × Remote 规则数」。不改竞速结构（禁区），15s 超时把窗口变为有界。

### 6.2 M1 修复设计（多规则中段失败不泄漏 listener）

- **缺陷现状**：`connect_and_forward` 的 listener 循环里 bind 失败用 `?` 提前返回，`listener_handles` 是局部 `Vec`，早退时 `JoinHandle` 被 detach（任务继续 accept、占住端口）；会话也未显式 disconnect。`probe_forwards` 任一端口 Free 即返回 Free，不保证全部可绑 → 后续轮次被自己上一次泄漏的任务挡住，永久重连失败。
- **修复机制（r7）**：
  1. 新增 `TaskSet(Vec<JoinHandle<()>>)`：`push()`、`abort_all()`（abort 后清空，幂等），`impl Drop` 调 `abort_all()`。
  2. `connect_and_forward` 的 listener 循环与 -R 分发任务全部登记进 `TaskSet`。bind 失败不再 `?` 直接返回，而是走统一错误路径：`tasks.abort_all()` → 显式 `session.disconnect(...)` → 返回 `Err(Retriable(bind 错误))`。
  3. `tcpip_forward` 申请失败发生在任何任务 spawn 之前，无任务可中止；该路径对「已申请条目」逐条 cancel + disconnect 后返回。
- **对正常路径零影响**：成功路径仍在 `select!` 退出后显式 `abort_all()`，随后 Drop 时空转（abort 幂等）；Local/Dynamic 的监听与转发逻辑逐字未变。
- **作证测试**：`TaskSet` 单测（Drop 会中止已注册任务；`abort_all` 幂等）；审读 `connect_and_forward` 的每个早退点均处在 `TaskSet` 生命周期内，或发生在创建任务之前。

### 6.3 L8 未知 kind 降级设计（必须随 v1.4 发布）

- **风险**：`ForwardKind` 是外部标签枚举，未来版本写出的新 kind（如 `"remote"` 被 v1.3 读、或 v1.5+ 新 kind 被 v1.4 读）会让 `serde_json::from_str::<Vec<TunnelConfig>>` 整体失败，`store.rs` 的 `unwrap_or_default()` 把整份列表静默读空（下次保存即永久丢失）。
- **方案（双层）**：
  1. **宽容枚举（r1）**：`ForwardKind` 增 `Unknown(String)`，手写 `Serialize`/`Deserialize`：已知三种写固定小写标签，未知字符串原样存入 `Unknown(raw)` 并原样回写——未来版本重新读到时能取回自己的 kind，升级/回退不再降级数据。
  2. **逐条容错（r4）**：`store.rs` 抽出私有 `parse_tunnels(&str) -> Vec<TunnelConfig>`，先解析为 `Vec<serde_json::Value>` 再逐条 `from_value`；单条失败只 `warn` 跳过该条，其余照常加载。整文件非法仍回退空表（与原行为一致）。**残余风险（记录）**：被跳过的坏条目在用户下次保存配置时不会写回——但宽容枚举已消除跨版本 kind 这一主要来源，剩余触发面仅为「单条 JSON 结构本身损坏」。
- **Unknown 规则行为定义**（r1/r7/r8）：

| 维度 | 行为 |
|---|---|
| 解析 | parser 永不产出 Unknown；仅由读入更高版本配置产生 |
| 连接 | 混合规则中跳过 + `tracing::warn!`；**全部规则不可用**（含空 forwards）→ `ConnectError::Fatal`「该隧道没有可用的转发规则（可能来自更高版本），请升级应用」，红灯、不重连 |
| probe / kill | `has_local_listener() == false` → 不探测、不 kill；全 Unknown 恒 `Free` |
| UI | 「目标」列显示「未知类型」；编辑器预览「未知转发类型（当前版本不支持）」；搜索不计 `remote_host`/`remote_port` |
| 配置保留 | 原 kind 标签与其余字段完整保留（导出/导入同样保留） |
- **版本限制（诚实说明）**：已发布的 v1.3 二进制读 v1.4 的 `kind:"remote"` 仍会整表清空——旧二进制无法回补。L8 的闭合面是「v1.4 及以后对未知 kind 宽容」，防的是 v1.5+ 与未来升级/回退组合。**回退指导（终态汇报列出）**：从 v1.4 回退到 v1.3 前，先备份配置目录下的 `tunnels.json`（`store.rs` 的 `config_dir()`，macOS 为 `~/Library/Application Support/sshmgmt/tunnels.json`），或先删除含 `-R` 规则的隧道。
- **步骤落点**：r1（枚举 + 运行期跳过臂）、r4（store 逐条容错）、r7（全不可用 Fatal）、r8（UI 标记）。

### 6.4 R1 门控锁定设计（评审 §7.3，推荐做）

- **缺口**：v1.3 修正后 `classify_channel_error` 有单测，但调用点「仅 Session 才 `notify_one()`」没有自动化锁定；把调用点改回无条件通知，现有 3 条测试仍全绿。
- **方案（r2）**：`socks.rs` 抽出 `fn notify_if_session_dead(err: &russh::Error, notify: impl FnOnce())`——分类为 Session 才调用闭包；调用点改为 `notify_if_session_dead(&e, || session_error.notify_one());`。单测用计数器闭包断言：`ChannelOpenFailure(_)` 各变体调用 0 次，`Disconnect`/`SendError`/`HUP` 各调用 1 次。
- **行为**：零变化（纯提取）。**作证**：`socks::tests` 新增 `target_level_failure_does_not_notify` / `session_level_failure_notifies_once`。

### 步骤 r7：-R 核心接线（B1/B2/B3 + M1 + 绿前置）

    ```rust
    let addr = f.remote_bind.clone().unwrap_or_else(|| "localhost".into());
    let requested = f.listen_port();
    let res = tokio::time::timeout(
        TCPIP_FORWARD_TIMEOUT,
        session.tcpip_forward(addr.as_str(), requested as u32),
    ).await;
    ```
    `Ok(Ok(allocated))` → 实际端口 = `requested != 0 ? requested : u16::try_from(allocated)`（转换失败按 Retriable 内部错误处理）；记录 `RemoteRoute`；`requested == 0` 的实际端口先暂存，**待全部规则申请成功后统一 `emit_notice(app, id, "success", 实际端口文案)`**（避免后续规则失败、条目被 cancel 后仍弹出误导性端口）。`Ok(Err(e))` / `Err(timeout)` → 对已申请条目逐条 cancel（3s 超时）→ `session.disconnect(...)` → `return Err(classify_...)`。

    ```rust
    while let Some(conn) = rx.recv().await {
        match routes.iter().find(|r| r.listen_addr == conn.listen_addr && r.listen_port == conn.listen_port) {
            Some(r) => { tokio::spawn(pump_forwarded(conn, r.target_host.clone(), r.target_port)); }
            None => tracing::warn!("forwarded-tcpip for unknown listener {}:{}", conn.listen_addr, conn.listen_port),
        }
    }
    ```
  - `async fn pump_forwarded(conn, host, port)`：`TcpStream::connect` 失败 → `warn` 后返回（channel 随 `conn` drop）；成功 → `copy_bidirectional(channel.into_stream(), tcp)`。**不通知 `session_error`**（会话死亡由 `disconnect_rx` 兜底）。

  - 新增 `TaskSet` 单测：`taskset_drop_aborts_registered_tasks`（任务持 `Drop` 标记，Drop 后断言已中止）、`taskset_abort_all_is_idempotent`。

### 11.1 关键时序与实现约束（来自方案 §5，逐条落到步骤）

```
run_tunnel 外层循环（零改动）
 └─ connect_and_forward
     ├─ 全不可用规则守卫（Fatal，零改动）
     ├─ select! 竞速区间（结构零改动）
     │   └─ establish_session
     │       └─ for (i, hop) in hops:                      // 逐跳串行
     │           ├─ i==0: connect_jump_host(hop)           // 直连 TCP
     │           ├─ i>0 : open_hop_session(prev, hop)      // 前链通道 + connect_stream，整段 15s
     │           ├─ phase1: 连接 A 仅公钥；失败显式 disconnect A
     │           ├─ phase2: 连接 B 密码/KBI（hop 标注）——A 与 B 的 MaxAuthTries 各自独立
     │           └─ chain.push(B 或 A)；disconnect_rxs.push(rx)
     │       └─ :22 预检（最终跳 handle，仅 Local）→ EstablishedSession{chain, disconnect_rxs, forward_rx}
     ├─ -R tcpip_forward 全部成功（最终跳 handle、15s）——失败 cancel + 逆序 disconnect + 分类返回
     ├─ 置 Connected
     ├─ 竞速区间外 spawn（TaskSet 托管）：
     │   ├─ 断线信号聚合任务（任一跳 → 单点信号）
     │   ├─ -L/-D listener（最终跳 handle）
     │   └─ -R 分发任务（forward_rx 来自最终跳）
     └─ 清理：abort 任务 → cancel(-R) → 最终跳 disconnect → 中间跳逆序 disconnect
```

1. **逐跳串行**：前一跳认证成功后才打开下一跳；任一跳失败即中止后续并清理已建链（逆序 disconnect）。
2. **每跳两阶段**：阶段一只试公钥、独立连接；阶段二换**全新连接**——首跳是新的 TCP+SSH，中间/最终跳是**经同一前链再开一条 direct-tcpip 通道**（不重连前面的跳）。每条连接是独立 SSH 会话，MaxAuthTries 预算独立，两阶段不变式保持。
3. **keepalive 每跳独立生效**：首跳与后续 `connect_stream` 共用同一份带 keepalive 的 `Arc<russh::client::Config>`（15s / max 3），但每条 SSH 连接各自独立计时——中间跳死亡由它自己的 keepalive 判死并触发 Drop 信号（C3 前提）。**不得**复用 `open_target_session` 里 `Config::default()`（无 keepalive，属一次性会话）。
4. **每跳超时**：`connect_jump_host` 与 `open_hop_session` 整段（开通道 + 握手）各 15s（沿用 `JUMP_CONNECT_TIMEOUT`）。最坏建链等待 = 15s × 跳数，已知取舍。
5. **连接/认证仍在竞速区间**：Stop/Reconnect 可在任意一跳的建连或密码等待期间立即生效（既有竞速结构不动）；取消时本地已建连接随 handle drop 关闭（与 v1.4 相同，不额外异步收尾）。
6. **断线聚合**：`forward_first_signal(rxs, tx)`——任一 `oneshot::Receiver` 完成（显式 `send` 或 sender drop）→ 发一次聚合信号并退出；内部 watcher 放进 `JoinSet`，聚合任务结束/被 abort 时 JoinSet drop 会自动中止剩余 watcher，无任务泄漏。`EstablishedSession` 只携带每跳原始 rxs；聚合任务由 `connect_and_forward` 在建立会话的竞速区间**之外**（establish 返回后、等待 select 之前）创建，不在 `establish_session` 内 spawn。select 语义保持 `Retriable("SSH session closed")`。
7. **清理顺序**：`abort` 任务 → cancel 服务器监听（最终跳、实际端口、3s 超时）→ 断开最终跳 → 中间跳**逆序** disconnect（避免前跳先断导致后跳产生误导性错误日志）。
8. **单跳零回归清单**：`hops.len()==1` 时——建链路径与 v1.4 等价；认证失败文案逐字相同；密码 payload 无 hop 字段、弹窗标题不变；密钥链账号仍为 `user@host:port`；列表/预览渲染与 v1.4 一致；导出 `password`/`target_user` 仍取同一台主机。
9. **通道归属**：`-L`/`-D` 的 `channel_open_direct_tcpip`、`-R` 的 `tcpip_forward`/`cancel`、`:22` 预检全部使用**最终跳** handle（v1.4 中唯一 handle 的直接延伸）。
10. **空链防御**：`hops` 为空（理论上迁移已保证非空）时返回 `Fatal("隧道缺少跳板配置")`，不 panic。
11. **已知取舍**：每跳密码提示仍为 5 分钟超时；多跳最坏等待为「15s × 跳数 + 5min × 需人工输入的跳数」；`-J` 列表语法仅 `[user@]host[:port]`，不支持 `none`/通配等扩展。

### 11.2 跨期交互（-R × -J，必须显式守住）

- **forward_tx 只注入最终跳**：只有最终跳的 handler 携带 `forward_tx`；中间跳一律 `None`。原因：`tcpip_forward` 只在最终跳申请，`forwarded-tcpip` 只会在该连接上到达；中间跳携带发送端虽无害，但会破坏「谁申请谁接收」的清晰不变量。
- **tcpip_forward 在最终跳申请**：`connect_and_forward` 用 `chain.last_mut()` 逐条申请，绿前置语义不变（全部成功才 Connected）；失败分类（`RequestDenied→Fatal`、其余→Retriable、超时→Retriable）与 Fatal 前收尾不变。
- **forwarded-tcpip 链路不变**：最终跳回调 → `forward_rx` → 既有分发任务按 `(listen_addr, listen_port)` 精确匹配 → `pump_forwarded`。分发代码零改动。
- **cancel 与清理**：`cancel_remote_forwards` 用最终跳 handle（经 `Arc<Mutex>`）；必须在最终跳 disconnect 之前；随后逆序断开中间跳。整体满足「abort → cancel → disconnect」且「链逆序」。
- **重连恢复（B2 延伸）**：`run_tunnel` 重跑 `connect_and_forward` → 重建整条链 → 重新逐条 `tcpip_forward`。多跳 + -R 的重连自动恢复无需额外状态。
- **:22 预检**：仍只对 Local + `:22`，且用最终跳 handle；`-R` 规则不参与。
- **已知边界继承**：v1.4 评审 M-2（地址漂移静默丢连接）与 M-3（半开重连 RequestDenied 直接红灯）在 -J 下语义不变，不新增处理，终态汇报沿用说明。
- **密码/密钥链归属**：每跳密码账号为 `hop.user@hop.host:hop.port`，天然不冲突；`-R` 目标主机的 `target_user` 账号仍按目标主机键，与跳数无关。

### 11.3 迁移与兼容设计（hops / legacy 双写 / L8 延续）

- **模型不变量**：`hops` 是唯一权威；`jump_user/jump_host/jump_port` 仅作 serde 镜像（读旧文件、写首跳）。运行时代码（tunnel/transfer/commands）一律走 `resolved_hops()` / `first_hop()`。
- **`ensure_hops(&mut self) -> bool` 语义**（幂等）：
  1. `hops.is_empty() && !jump_host.is_empty()` → `hops = [Hop{legacy 三字段}]`；
  2. `hops` 非空 → 用 `hops[0]` 覆写 legacy 三字段（修复旧版本/手工编辑造成的镜像漂移）；
  3. 返回是否发生任何修改。
- **启动迁移入口**：`lib.rs::run()` 在 `load_tunnels()` 与 `migrate_env_case()` 之后、`TunnelManager::new` 之前调用 `if migrate_hops(&mut tunnels) { save_tunnels(...) }`；保存失败只 `warn`，不阻断启动（与 `migrate_env_case` 同模式）。
- **导入迁移**：`commands::import_tunnels` 对每条配置先 `ensure_hops()`，再写跳密码与 target_user。旧导出文件（无 hops）经此变成单跳；新导出文件（有 hops）原样保留。
- **L8 宽容语义延续**：`hops` 与 `hop_passwords` 均为 `#[serde(default)]` 的可选新增字段；未来版本新增字段不会让本版本解析失败；未知 `ForwardKind` 仍原样保留。
- **回滚镜像**：旧版本（v1.4）读新配置时按 legacy 三字段得到「首跳单跳近似」——多跳隧道回退后只会直连入口跳，转发不可用但不崩溃（决策③/待裁决项 3 已接受的代价）。**回退前建议先备份 `tunnels.json`**。
- **已知遗留（不在本期修）**：`transfer` 的 `target_user` 导出/导入键沿用 legacy/first_hop，而运行期实际键是目标机 `host:port`——这是 v1.2 起的既有不一致，导出格式只有单值 `target_user` 字段无法表达多目标；v1.5 仅做机械迁移，登记为已知限制。
