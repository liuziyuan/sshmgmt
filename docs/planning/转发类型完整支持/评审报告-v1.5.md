### 1.3 轻微（6）

#### L1 文档注释错位：`password_phase` 的文档被并入 `password_payload`

- **证据**：`src-tauri/src/tunnel.rs:1224-1238`。原本属于 `password_phase` 的文档块（1224-1235，"Authenticate a session against `host:port` …"）与 `password_payload` 的文档块（1236-1238）之间没有空行，两段连成一体，最终整段挂到 `fn password_payload`（1239）上；`async fn password_phase`（1261-1262，带 `#[allow(clippy::too_many_arguments)]`）反而失去文档。
- **影响**：`tunnel.rs` 的认证函数是项目 CLAUDE.md 明确要求"改这部分前务必通读"的敏感区域；现在 `password_payload` 的 rustdoc 以认证策略开头、`password_phase` 无文档，会直接误导后续维护者。无运行时影响。
- **修复**：在 tunnel.rs:1235 之后补一个空行，恢复两段文档的归属（零代码行为）。

#### L2 `SshClientHandler.forward_tx` 字段注释过时（计划 t4 要求同步更新）

- **证据**：`src-tauri/src/tunnel.rs:37-39` 仍写 "Present only on the **primary jump-host connection** when the tunnel has Remote rules"；而实际语义已变为"仅**最终跳**携带"——`hop_forward_tx = if is_final { forward_tx.clone() } else { None }`（`tunnel.rs:779`），中间跳一律 `None`。《实施计划》步骤 t4 明确要求"同步更新 `SshClientHandler.forward_tx` 与 `establish_session` 的文档注释（「最终跳携带、逐跳链」）"。
- **影响**：注释与新语义矛盾，正好落在 -R×-J 的关键不变式（"谁申请谁接收"）上；无运行时影响。
- **修复**：把该字段注释改为"仅最终跳连接携带；中间跳为 None"，与 `tunnel.rs:760-762` 及 §11.2 一致。

#### L3 `ForwardSpec::target()` 的 `#[allow(dead_code)]` 理由已失效

- **证据**：`src-tauri/src/model.rs:174-177` 注释称 "it is expected to be needed by v1.5"；v1.5 已收口，全仓搜索 `target()` 只命中测试（`parser.rs` 5 处、`model.rs` 9 处），无任何生产调用点（-R 分发走 `RemoteRoute`，-L 直接用 `remote_host/remote_port`）。这是 v1.4 评审 L-1 的延续项，其保留理由（"v1.5 可能有生产调用方"）已不成立。
- **影响**：注释误导；`allow` 本身在非测试构建下仍是消除 dead_code 的必要手段，可保留，但理由需订正。无运行时影响。
- **修复**：删除"expected to be needed by v1.5"表述（或直接移除该方法及其 allow）。二选一，均为零行为。

#### L4 `build_export` 对首跳密码重复读取钥匙串

- **证据**：`src-tauri/src/transfer.rs:62-70`——`hop_passwords` 已对全部跳（含首跳）调用 `store::get_password`；随后 `password` 又对 `hops.first()` 再读一次。
- **影响**：仅一次多余钥匙串读取，无功能影响；两次读取之间若钥匙串被外部修改，`password` 与 `hop_passwords[0]` 可能出现极小的不一致。
- **修复**：`password = hop_passwords.first().cloned().flatten()`（或复用首跳读取结果）。

#### L5 测试覆盖缺口（2 处，均不阻塞）

- **5a**：`src-tauri/src/transfer.rs:328` 的 `multi_hop_export_keeps_hops_order` 只断言 `TunnelSecret` 的序列化结构，不触达 `build_export` 中 `resolved_hops()` 的接线。若日后有人把 `build_export` 改回读 legacy 三字段，现有测试不会失败。计划 t6 原文允许"不触钥匙串"，故属计划内取舍；建议将"按 hops 顺序取密码"抽成可注入的纯函数/辅助，以便锁定。
- **5b**：`src-tauri/src/tunnel.rs:1706-1732` 的 `forward_first_signal` 两条测试只验证"任一 rx 触发/发送端 drop 即发出"，未断言"多跳同时断开只发一次"的去重语义（当前实现 `join_next().await.is_some()` 结构上确实只发一次，但无测试锁）。

#### L6 `执行台账.md` 残留重复行（文档，主控维护）

- **证据**：`docs/planning/转发类型完整支持/执行台账.md:38-41`——第 38/39 行已是 S2c（已完成）/S3c（在跑），第 40/41 行又出现一份"S2c 待派发 / S3c 待派发"的陈旧副本。这是 v1.4 评审 L-6 同类问题的复发。
