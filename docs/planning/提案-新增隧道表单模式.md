# 提案：新增隧道支持表单填写模式

> 状态：已确认（2026-11-19 讨论定稿），待实施
> 关联：`src/components/TunnelEditor.tsx`、`src-tauri/src/parser.rs`、`src/api.ts`
> 读者：后续实施者

## 0. 一句话结论

在新增/编辑隧道弹窗顶部加「表单填写 / 粘贴命令」双 Tab；表单模式由**前端把字段拼装成一条规范 ssh 命令**，走与粘贴模式完全相同的 `parse` → 保存链路——后端零改动，旧隧道、导入导出天然兼容。

## 1. 问题

当前新增隧道只能粘贴一条完整的 `ssh -L` 命令。对不了解 SSH 端口转发概念的新人不友好：他们不清楚跳板机、转发、各字段的含义，也不知道一条合法命令长什么样，实际上被挡在了功能门外。

## 2. 现状核对

| 事实 | 出处 |
|---|---|
| 新增和编辑都以 ssh 命令字符串为唯一入口，保存前先解析成结构化配置 | `TunnelEditor.tsx` 的 `handleSave`、后端 `add_tunnel` |
| `TunnelConfig` 本身是结构化的（跳板机用户名/地址/端口、转发列表、`bind_all`、`identity_file`），`raw_command` 只是原始命令备份字段 | `src/types.ts` / `src-tauri/src/model.rs` |
| 解析器已支持：多 `-L`、`-p`、`-i`、`-g`、含 `@` 的用户名、IPv6 方括号地址 | `parser.rs` 及其单测 |
| 编辑弹窗目前回填命令串，保存时重新解析 | `TunnelEditor.tsx` |

## 3. 方案

### 3.1 交互形态：弹窗内双 Tab

```
┌─ 新增隧道 ──────────────────────────────┐
│  [表单填写]  [粘贴命令]   ← 顶部切换      │
│ ┌─────────────────────────────────────┐ │
│ │ （表单模式）                          │ │
│ │  跳板机（你能直接登录的那台机器）        │ │
│ │   用户名 [_______]  地址 [________]   │ │
│ │   端口 [22__ ]                       │ │
│ │                                      │ │
│ │  转发规则（可添加多条）                 │ │
│ │   本地端口 [10008] 目标主机 [____]     │ │
│ │              目标端口 [3306]   [删除]  │ │
│ │   ＋ 添加一条转发                      │ │
│ │                                      │ │
│ │  ▸ 高级选项（默认折叠：-g、私钥路径）    │ │
│ │                                      │ │
│ │  显示名称 / 分组 / 环境（现有字段不动）  │ │
│ └─────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

- **表单模式**：每个字段带中文说明文案。关键文案是「目标主机」——必须写明"**这是从跳板机看过去的地址**，不是你电脑上的 localhost"，这是新人最容易配错的点。
- **粘贴命令模式**：现有 textarea + 解析预览，原样保留。
- **双向转换**：切 Tab 时自动互转——命令粘贴后切到表单能看到拆解结果（调 `parseCommand` 回填）；表单填完切到命令能看到等效命令（本地拼装）。后者本身有教学价值：新人用几次表单，自然看懂 ssh 命令结构。

### 3.2 数据链路：前端拼命令，复用现有解析（核心取舍）

表单保存时，前端把字段拼成一条规范命令（如 `ssh -N -L 10008:host:3306 -p 2222 user@jump`），走和粘贴模式完全相同的 `addTunnel` / `parseCommand + updateTunnel` 路径。

**为什么不在后端新开"直接收结构化数据"的接口**：现有系统里编辑、导入导出、持久化全都以 `raw_command` 为源头，新开接口意味着后端多处改动、前后端类型双份同步、导入导出兼容性验证，而这些成本买不到任何用户可见的收益。走拼命令这条路，后端一行不改，旧数据零风险；表单生成的命令串导出后还能直接在终端用，是附赠价值。

**往返一致性保障**：表单字段是受控输入（端口限数字、主机名/用户名禁止空格），拼出的命令是规范格式，保存前照常调 `parseCommand` 校验，保证"拼出的命令解析回来 = 表单里填的"。

### 3.3 编辑模式的回填

编辑已有隧道时，表单直接用 `editTarget.config` 的结构化字段回填（含 `identity_file`、`bind_all`），**不做命令反解**；只有用户切到命令 Tab 才看命令原文。粘贴命令创建的旧隧道因此自动获得完整的表单编辑能力。

## 4. 边界与不变式（验收标准）

1. **配置等价**：表单模式创建的隧道，与粘贴等价命令创建的隧道，最终 `TunnelConfig` 完全一致（除自动生成的 id/name 外）。
2. **往返一致**：表单值 → 拼装命令 → `parseCommand` 解析回的结构化字段，与表单输入逐字段相等（含多条转发、`-g`、`-i`、自定义端口）。
3. **表单校验**：端口必须是 1–65535 的数字；主机地址、用户名、目标主机非空且不含空格；转发规则至少一条。不合法时保存按钮禁用或提示，不产生非法命令。
4. **编辑回填**：粘贴命令创建的旧隧道，编辑时表单各字段（含高级选项）正确回填，保存后不丢配置。
5. **Tab 双向转换**：两个方向切换都不丢数据；转换失败（如命令解析报错）时给出明确提示且不覆盖另一侧已有内容。
6. **默认 Tab**：首次打开默认表单；之后记住用户上次的选择（本地偏好存储）。
7. **兼容性**：粘贴命令模式行为与现状完全一致；后端无任何接口/模型变更（`types.ts` / `model.rs` 不动）。
8. UI 文案全部中文，符合仓库既有约定。

## 5. 决策项与取舍（已定结论）

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| 1 | 默认 Tab | 默认表单 + 本地记住上次选择 | 目标人群是新人，首次必须落在表单；老用户切一次命令 Tab 后下次直接停在命令 Tab，两类人都零额外操作。 |
| 2 | 高级选项折叠区内容 | `-g`（监听所有网卡）+ 私钥文件路径 | 两者后端已支持但新人 90% 场景用不到；折叠既不丢能力又不吓退新人。`auto_reconnect` 现有界面就不可改（恒为开），不进表单。 |
| 3 | 数据链路 | 前端拼命令，复用现有 `parse` 链路，后端零改动 | 见 §3.2；备选"后端新结构化接口"成本高且无用户可见收益，已否决。 |
| 4 | 编辑回填来源 | 直接用结构化字段，不反解命令 | 结构化字段就在 config 里，反解引入额外失真面。 |
| 5 | Tab 切换时是否互相同步 | 是，双向自动转换 | 让命令 Tab 始终可见等效命令，对新人有教学价值。 |

## 6. 风险与对策

- **表单校验不完备导致拼出非法/歧义命令**：对策是 §4.2 的往返一致性校验（保存前 `parseCommand` 复核）+ §4.3 的输入约束（禁空格、端口限数字）。主机名含 `:`（IPv6）时拼装需按解析器约定加 `[]`。
- **Tab 转换丢数据**：对策是转换失败时不覆盖目标侧内容、给出提示（§4.5）。

## 7. 不做什么（非目标）

- 不支持 `-J`（ProxyJump）、`-D`、`-R`——与 `parser.rs` 现状对齐，表单不提供这些入口。
- 不做隧道模板、连接向导等更重的引导。
- 不改后端数据模型与接口。

## 8. 实现清单（供后续实施者）

全部改动集中在前端，预计只动 `src/components/TunnelEditor.tsx`（可能新增一个同级组件文件）：

1. **Tab 状态**：弹窗顶部双 Tab；上次选择持久化到 `localStorage`（key 自定，如 `sshmgmt.editor.mode`），首次默认表单。
2. **表单状态建模**：跳板机用户名/地址/端口（默认 22）、转发规则数组（本地端口/目标主机/目标端口，可增删、至少一条）、高级折叠区（`bind_all`、`identity_file`）。显示名称/分组/环境沿用现有 state，两种模式共享。
3. **拼装函数 `formToCommand`**：按规范格式输出 `ssh -N [-L lport:rhost:rport ...] [-p port] [-i path] [-g] user@host`；host 含 `:` 时按 `[]` 包裹；`identity_file` 路径含空格时用引号包裹。
4. **校验**：§4.3 的约束；校验结果驱动保存按钮可用性与错误提示。
5. **编辑回填**：打开时若为编辑模式，用 `editTarget.config` 结构化字段填表单 state（命令 Tab 仍回填 `raw_command`）。
6. **Tab 双向转换**：命令→表单调 `parseCommand` 回填；表单→命令调 `formToCommand` 写入命令框；失败时提示且不覆盖。
7. **保存路径**：表单模式下 `formToCommand` → 复用现有 `addTunnel`（新增）或 `parseCommand + updateTunnel`（编辑）逻辑，不新开后端调用。
8. **验收自查**：`npx tsc --noEmit` 通过；按 §4 逐条核对（重点：往返一致性、旧隧道编辑回填）。

## 已知边界（记录在案，不随本提案解决）

- 粘贴命令里若带四段式 `-L`（`bind:lport:rhost:rport`），现有解析就会丢弃绑定地址——这是既有行为，表单编辑后保存不会更差。
